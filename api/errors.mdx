title: 'Errors and retries'
description: 'Use HTTP statuses and actionable JSON field errors.'
---

V2 API errors return JSON, including when the `Accept` header is omitted.
Use the HTTP status to decide whether to correct your request or retry it.

| Status | Meaning | Action |
| --- | --- | --- |
| 200 | Request succeeded | Read the response body |
| 400 | Query parameters are nested too deeply | Reduce nesting in query parameter names |
| 401 | Authentication failed | Check your Bearer token |
| 403 | API access or a token permission is missing | Check the project and token permissions |
| 404 | Project/location was not found or is outside your access | Check both public IDs and project membership |
| 422 | Request validation failed | Correct the named fields |
| 429 | Rate limit reached | Wait for `Retry-After` |
| 500 | Server error | Check the result before retrying a write |

## Query parameter nesting

When query parameter names exceed the supported nesting depth, the request returns `400` with the message `Reduce query parameter nesting to the supported limit.` Correct the query before retrying.

This limit applies to parameter names. Square brackets inside a parameter value remain supported.

## Validation errors

```json
{
  "message": "The city field is required.",
  "errors": {
    "city": ["The city field is required."]
  }
}
```

The `message` summarizes the failure. The `errors` object identifies each invalid field; messages can differ depending on the request.
A rejected V2 location update does not save a subset of its fields.

### Empty hours and incomplete weeks

`"hours": {}` is valid and leaves hours unchanged. `"hours": []` is invalid: hours must be a weekday object.

A nonempty POST or PUT hours object must include all seven days. Use PATCH to update selected days instead:

```json
{"hours":{"mon":"09:00-17:00"}}
```

Weekday values are strings or null, not objects such as `{"open":"09:00","close":"17:00"}`. See [opening hours](/api/locations/update#opening-hours).

## Rate limits and retries

The current shared API limit is 1,000 requests per minute. Read `X-RateLimit-Limit` and `X-RateLimit-Remaining` on responses; a `429` also includes `Retry-After`.
Wait for that interval before retrying, and space subsequent requests out.

Retrying a POST can create another location if the original request succeeded before the connection failed. Check whether the location already exists before retrying a create.

## Addresses and coordinates

`lat` must be between -90 and 90; `lng` must be between -180 and 180. Zero is valid. The returned address field is `address`.

POST and PUT can geocode synchronously when either coordinate is missing or zero. Both accept zero during validation but retain this older geocoding behavior.

**Changing an address moves the pin.** When an update changes `address`, `address_line_1`, `address_line_2`, `city`, `state`, `postcode` or `country` and sends neither `lat` nor `lng`, StoreRocket looks up the new address. The pin moves when the new address is more than 100 meters from the old one. A reworded address in the same place, such as `St` to `Street` or a new suite number, keeps the existing pin, including one placed by hand. If the new address cannot be found, or geocoding is temporarily unavailable, the pin and the location's visibility stay as they were.

**An address found only roughly counts as not found.** For an address the geocoder cannot find, it often returns something rougher instead of no result: the whole country, the town, the postcode area, the road or a nearby business. When the new address names a street and only such a rough match comes back, or only its country or region, the pin and visibility stay as they were. The new address itself is still saved. A misspelled street that still finds the building moves the pin. Updates to a location that is only a town, such as `"city": "Uppsala"` with no street, still move the pin to the new town.

- V2 PUT moves the pin during the request. The response contains the new coordinates and a [`geocoding`](#the-geocoding-object) object saying what the lookup found.
- V2 PATCH and V1 PUT move the pin shortly after the response, which still shows the previous coordinates.

**Coordinates you send always win.** Include `lat` and `lng` to place the pin yourself; the address is then not looked up. Sending the location's current coordinates with a new address keeps the pin where it is. To let StoreRocket place the pin from the address, omit `lat` and `lng`, or send `"lat": null, "lng": null` to clear the pin and geocode the address as for a new location. If a cleared pin's address cannot be found, the coordinates stay null and the location is hidden (`visible: false`) until it has coordinates.

A PATCH affecting address or coordinate fields also queues geocoding when a coordinate is missing; it preserves supplied zero coordinates. The immediate response can still have null coordinates. Changing a phone or other unrelated field does not trigger geocoding.

### The geocoding object

Every V2 create, PUT and PATCH response includes `geocoding` next to `data`. It describes the address lookup made by that request, and is `null` when the request looked nothing up.

```json
{
  "data": {
    "id": "...",
    "lat": 59.3326,
    "lng": 18.0649,
    "visible": true
  },
  "geocoding": {
    "status": "approximate",
    "match": "country"
  }
}
```

| `status` | Meaning |
|---|---|
| `found` | The address was found. The pin is at it, or stayed because the new address is within 100 meters of the old one. |
| `approximate` | Only a rough match was found: the country, region, town, postcode area, road or a nearby place, not the address. An existing location keeps its pin; the new address is saved. A new location, or one whose pin you cleared, is placed at that point; correct its address or send `lat` and `lng`. |
| `not_found` | No match. An existing location keeps its pin. A new location, or one whose pin you cleared, has null coordinates and is hidden. |
| `unavailable` | Geocoding was temporarily unavailable. The coordinates are unchanged and the new address is saved. StoreRocket looks the address up again a few minutes later and moves the pin then, by the same rules. |
| `queued` | PATCH only: the lookup runs shortly after the response, by the same rules, so this response cannot say what it found. Use PUT when your integration needs the answer. |

`match` says what was matched: `address`, `road`, `place` (a business or landmark), `postcode`, `city`, `region` or `country`. It is `null` for `not_found`, `unavailable` and `queued`.
